# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local tool for laying out bedroom furniture on a 2D floor plan. There is no bundler, lint, or test setup (`--build` only bakes data into a standalone page) — just Node (>=20) and a few source files. The 3D view loads three.js from jsdelivr, so it needs internet access.

The layout itself has no dependencies; `npm install` is only for the three SDKs that turn the 3D view into a photo (`@anthropic-ai/sdk`, `@google/genai`, `openai`), loaded on demand by `src/render.mjs` when someone renders. Everything else runs with an empty `node_modules`.

**This repo is only the program.** The room and furniture files are a separate project, named on the command line at startup (this working copy uses `C:\git\bedroom-data`, via the `DATA_DIR` user env var):

```
node src/server.js <data-dir> [--open]       # or: npm start -- <data-dir>
npm start        # node src/server.js --open  (serves and opens the browser)
npm run serve    # node src/server.js         (no browser)
npm run build    # node src/server.js --build (write <output-dir>/furniture-layout.html, standalone, no server needed)
npm run photos   # node src/fetch-photos.js [filter...] [--data dir] [--all] [--force] [--out dir]
```

The data dir comes from the first positional argument or `-d`/`--data`, else `$DATA_DIR`, else `../data` next to the program; command-line options win over the environment. A missing data dir is fatal (exit 1 with usage) rather than an empty room. Pointing at a data *project* root works too: if the folder has no `room_layout.json` but its `data/` subfolder does, `resolveDataDir` descends into it (both `server.js` and `fetch-photos.js`).

Generated files go to `-o`/`--output`, else `$OUTPUT_DIR`, else `defaultOutputDir()`: the sibling `output/` of a data folder literally named `data`, otherwise `<data-dir>/output`. That covers placements, renders and (via `--out`'s default) downloaded photos. `PORT` (default 3000) and `HOST` (default 127.0.0.1) are env-only. `node src/server.js --help` prints all of it.

API keys for rendering are read from `.env` by `loadEnv(...dirs)`, which tries the data folder first, then the project around it (so `<project>/.env` sits beside `data/` and `output/`), then this repo — the first file to set a name keeps it, and a real environment variable overrides all of them. It runs straight after `DATA_DIR` is resolved, which is the one setting a `.env` can't provide, and before `OUTPUT_DIR` and everything else, which it can. Keys: `GEMINI_API_KEY` and/or `OPENAI_API_KEY` for the image model, `ANTHROPIC_API_KEY` for Claude's optional passes, plus `RENDER_PROVIDER`, `RENDER_MODEL_GEMINI`, `RENDER_MODEL_OPENAI` and `RENDER_PROMPT_MODEL` to override the defaults. Note that `HOST=0.0.0.0` exposes a route that spends money.

```
src/      the whole program: server.js, render.mjs, fetch-photos.js, furniture-layout.html, room3d.html
```

A data project looks like this (`data/` + `output/`, the layout `defaultOutputDir` expects):

```
<project>/data/     input: room_layout.json, material_colors.json, furniture/, rugs/
<project>/output/   generated, git-ignored: furniture_placements.json, photos/, renders/, layout-<timestamp>.json|png|zip, layout-site-<timestamp>.zip (exports)
```

## Architecture

- **`src/server.js`** — plain `http` server. Serves `furniture-layout.html`, serves `room3d.html`, returns all project JSON in one call (`GET /api/project` → `{ dataDir, files: [{ path, text }] }`: `room_layout.json`, `material_colors.json` and every `.json` under `furniture/` and `rugs/` from `DATA_DIR`, plus `furniture_placements.json` from `OUTPUT_DIR`). Paths are sent relative to the data dir (e.g. `furniture/room_and_board/hudson_dresser.json`), and the placements file is sent under its bare name, so the client doesn't need to know about the folder layout; `dataDir` is the resolved absolute path, used only in the client's "not found" message (`state.dataDir`). The response also carries `photos`: product path minus `.json` → the main photo URL (`photos/<path>/<file>`, the `product` entry of each `sources.json` under `<OUTPUT_DIR>/photos/` that `fetch-photos.js` writes), which `GET /photos/...` serves (images only) and the **Selected** panel shows as a thumbnail (`state.photos`, `renderInspector`). The photos folder isn't watched, so new photos show up on the next reload. The server also writes placements (`PUT`/`POST /api/placements` → `OUTPUT_DIR`, which is created if it's missing; POST exists for `navigator.sendBeacon` on unload), writes the page's exports (`POST /api/export?name=layout-<YYYYMMDDTHHMMSSZ>.json|png`, raw body up to 50 MB, into `OUTPUT_DIR`; any other name is a 400), writes zip exports (`POST /api/export-zip?name=…&content=data|site`: `exportZip()` → `writeExportZip(name, mainFile, photoUrls)`, the one shared path that zips a main file with the `photos/…` it refers to, via the dependency-free `makeZip()`; `data` = the posted Export data JSON + photos of the products it lists, looked up in `readPhotos()` rather than trusting client paths; `site` = `buildPage()` — the same function `--build` uses, with the posted placements — as `index.html` + every product photo; image entries are stored, not deflated), renders the 3D view's point of view as a photo (`POST /api/render` → `render.mjs`, below; `GET /api/render/config` says which providers have keys, never the keys themselves; `GET /api/renders` lists every saved render's `meta.json`, newest first; `GET /renders/...` serves the images, through the same `sendImage()` containment-and-images-only helper as `/photos/...`) and pushes SSE on `GET /api/events` (`broadcast(event, data)` carries a JSON payload now — `change` and `page` still send `{}`, `render` reports each stage). A recursive `fs.watch` on `DATA_DIR` broadcasts `change` when the room, colors, furniture or rug files change. A second watch on `src/` broadcasts `page` when either HTML file changes, and both pages reload themselves. `OUTPUT_DIR` isn't watched, so writes to `furniture_placements.json` are intentionally *not* broadcast.
- **Standalone build** (`server.js --build`, `buildPage()`) — resolves `DATA_DIR`/`OUTPUT_DIR` like the server, then writes `<OUTPUT_DIR>/furniture-layout.html` instead of listening: the layout page with `window.FURNITURE_LAYOUT_EMBEDDED = { built, dataDir, files, photos, room3d }` injected before `</head>` (`files` and `photos` are exactly what `/api/project` returns; the photo URLs are relative, so they resolve against `photos/` beside the built page; `room3d` is the 3D page's text with `window.FURNITURE_LAYOUT_STANDALONE = true` injected; JSON has `<` escaped). The page works from `file://`: `initStandalone()` loads `EMBEDDED.files`, edits save to localStorage (`furnitureLayout.standalone.placements`, `{ base, saved, text }`, where `base` hashes the baked-in placements so a rebuild with different placements wins over older browser edits), the export buttons download their files, and the Project panel swaps **Reload files** for **Download placements** / **Reset to built layout**. The 3D popup is opened from a blob: URL and fed with `postMessage` between the two windows rather than the BroadcastChannel, which isn't dependable under `file://`.
- **`src/furniture-layout.html`** — the entire client (HTML + CSS + one inline `<script>`, SVG rendering, no framework). The server sends raw file text; all parsing/validation happens client-side in `parseRoom` / `parseFurniture` / `loadProject`. Edits are debounced (`commit()`) and saved through the server. The **Export data** / **Export image** buttons (stacked in the bottom-right corner of the plan) save `layout-<ts>.json` (`buildExport()`: the room file, material colors, each product in the room (count > 0) with its file, count, color and price, `buildPlacements()`, and total price per currency) and `layout-<ts>.png` (`renderPlanPng()`: the SVG cloned with the page stylesheet inlined, selection UI stripped, drawn to ~3000px with non-scaling stroke widths/dashes scaled to keep their on-screen weight); `<ts>` is ISO-8601 basic UTC (no colons, for Windows). A standalone build downloads them instead. **Export zip** (`layout-<ts>.zip`: that JSON, whose products carry a relative `photo`, + their photos) and **Export site** (`layout-site-<ts>.zip`: the standalone page as `index.html` + all photos; the page posts `placementsText()` and `buildPage(placementsText)` bakes those in place of the file on disk, so the site matches the screen even if the last autosave failed) go through `/api/export-zip` and are hidden in a standalone build. View prefs (snap, grid, rail widths, collapsed panels/groups, ledger open) go to `localStorage`.
- **`src/room3d.html`** — walk-through 3D view (three.js + `PointerLockControls`, one inline module), opened as a popup by the **3D view** button. It has no data access of its own: the layout page posts the whole scene (`{ type: 'scene', room, colors, items }`, items carry their raw file as `doc`) on the `furniture-layout-3d` BroadcastChannel after every `refreshAll` / `refreshMoving` (throttled by a timer, not rAF, so it works from a background tab) and whenever the popup sends `hello`. All layout tabs share that channel, so scenes carry `source` (the posting tab's id, kept in `sessionStorage`); the popup is opened as `room3d.html?source=<id>`, ignores scenes from other tabs, and only that tab answers its `hello` — otherwise a stale tab (e.g. an old one left by `--open`) snaps the 3D view back to its old layout. Shapes are built per type in `buildPiece` (bed / case goods / chair / rug / box) from `furniture.dimensions` and optional `geometry.*` fields. `window.view3d` exposes `{ THREE, scene, camera, renderer }` for poking at it from DevTools. The camera pose is kept in `sessionStorage` (`furnitureLayout3d.pose`, restored in place of `goHome()` on the first scene), because a `page` reload would otherwise lose the point of view a render is tied to.
  The **Render this view** panel (top right, `!STANDALONE` only, prefs in `localStorage` under `furnitureLayout3d.prefs`) sends one shot to `POST /api/render`: `capture(w, h, draw)` resizes the drawing buffer, draws and reads it in one synchronous block (there's no `preserveDrawingBuffer`, so a later `toDataURL` would come back blank), once for the photo-sized geometry pass and again through `withMask()` — every piece flat-shaded in its own colour, the room black — whose small `WebGLRenderTarget` readback is counted per colour by `measureMask()` to get each piece's share of the frame and screen box *including occlusion*, which projecting a bounding box can't do. `#frameGuide` marks what will be captured: the capture aspect only differs sideways, since a `PerspectiveCamera` keeps its vertical field of view, so the guide and the `#renderOverlay` that fades the finished render over the live geometry (<kbd>V</kbd>, hold <kbd>B</kbd>) are exact. <kbd>P</kbd> renders; double-clicking a thumbnail stands the camera back where that render was taken.
- **`src/render.mjs`** — the render pipeline, imported on demand by `POST /api/render` (ESM, and the only thing that needs `node_modules`). `renderView(request, ctx)`: picks each in-frame product's best appearance photo from its `sources.json` under `<output>/photos/` (`product` → `product-alt` → `room` → `gallery` → `detail`, never `dimensions`; smallest file among equal kinds; one product's photos serve all its pieces; capped at 6 photos / 12 MB) → builds a deterministic brief with `buildPrompt()` — room and camera in feet and inches, then every piece largest-first with its materials resolved to hex through `material_colors.json`, its distance, bearing, which face the camera sees, its share of the frame, and which image is its reference (plus that photo's `page_config`, so the model is told which variant it shows), then the pieces that are *not* in frame so they don't get invented → optionally has Claude Opus 5 tighten the brief (adaptive thinking, streamed; a refusal or an error falls back to the deterministic draft) → asks the image model for the picture (`gemini` via `ai.interactions.create` with `response_format: { type: 'image', mime_type: 'image/jpeg', aspect_ratio }` — JPEG is the only output that endpoint accepts — `openai` via `images.edit` with `input_fidelity: 'high'`; one small adapter each, model ids from the environment, and the saved file is named for the format that actually came back) → optionally has Claude compare the result against the geometry pass and list what drifted. Everything lands in `<output>/renders/render-<YYYYMMDDTHHMMSSZ>/`: `pov.png`, `mask.png`, `prompt.txt` (+ `prompt-claude.txt`), `render.png`, and `meta.json` with the pose, the per-piece measurements, the references used, timings and usage. The inputs are written *before* the image call, and a failure still writes `meta.json` with its `error`, so a render that didn't work can still be read.
- **`src/fetch-photos.js`** — standalone CLI, not used by the app. For each product file in `DATA_DIR` it scrapes `metadata.source_variant_url` (else `product_url`) and saves the photos to `<output-dir>/photos/<product path minus .json>/` (`--out` overrides that folder and is resolved against the current directory), named `NN-<kind>[-caption].<ext>` (git-ignored), plus a `sources.json` with each photo's URL and caption. By default only the main `product` photo is saved; `--all` adds the other kinds: `detail`, `dimensions`, `room` (Room & Board, from `__NEXT_DATA__` media sets via Scene7, which caps at 4000px and serves WebP), `gallery` (Article, everything under `cdn-images.article.com/products/SKU<id>/`); other sites fall back to JSON-LD / `og:image`. The Room & Board `product` render is `configurationOverride.imageData[<article>]`, which only exists when the URL carries `CHAR_*` options, else the JSON-LD image (the page default); `configurationOverride.defaultProduct` is the *unconfigured* default and must not be used. Pages with variants but no `CHAR_*` options (rugs: size → style → colour) are resolved through `productPageModel.combinedProductSelector`: the leaf whose titles all appear in the file's name/size/materials (hidden `renderer: "NONE"` levels such as "Material" are ignored) gives the article, and `<collection>/<article>` is fetched instead (logged as `using variant`, recorded as `page_url`); URLs with `CHAR_*` are taken as given. It also warns when a `wood`/`species`/`fabric`/`color` value from the file's `materials` isn't in the page's configuration. Re-runs reuse files already on disk by URL and prune ones not kept this run (so a run without `--all` removes earlier extras). It warns when the page's product title differs from the file's `furniture.name`, which usually means a collection URL landed on another size or colour, and for Room & Board prints the page's configuration in words (`page_config` in `sources.json`) to compare against the file's materials.

## Data files

All input lives in the data dir (see above). The paths below are relative to it.

- **`room_layout.json`** — room `width`/`length` (with `*_feet` fallbacks), `openings` (windows/doorways) given by `start`/`end` points on a wall. Only a southwest origin with x = east, y = north is supported. Doorways/entrances are drawn as plain openings (no door leaf in 2D or 3D, no clearance check). Optional `colors` (`walls.{north,south,east,west}`, `ceiling`, `floor`) names surface colors for the 3D view; the names are looked up in `material_colors.json` `materials`, falling back to `defaults.wall/ceiling/floor`.
- **`furniture/<vendor>/<item>.json`** and **`rugs/<size>/<item>.json`** (e.g. `rugs/9x12/`) — one file per product, same format. Everything under `rugs/` is a rug (drawn under furniture, exempt from overlap checks against furniture) and is listed in its own Rugs section, grouped by size folder then manufacturer. The client uses `furniture.dimensions` (`width` × `depth`, or `width` × `length` for rugs), optional `furniture.size` (appended to plan/ledger labels to tell variants apart), optional `furniture.shape: "round"` (drawn as an ellipse inscribed in width × depth in the plan and as a tub chair in the 3D view; its ellipse is the footprint everywhere — overlaps, walls, window sill and snapping — via `outline` / `halfExtents`, so rotating it changes nothing), `furniture.type` (drives default placement: beds → west wall, dressers/bookcases → east wall), `manufacturer` (list grouping), `metadata.price.configured_price`, optional `selected: true` (+ optional `quantity`) for a non-zero starting count, and `units` (inches/ft/cm/mm/m all accepted). Everything else (materials, construction, notes) is informational. Files are often *alternatives* for the same spot, so each file is a *product* whose count starts at 0; the list's −/+ stepper sets how many *pieces* of it are in the room.
- **`material_colors.json`** — `materials`: material/finish name → hex (case-insensitive), `defaults`: fallback colors for parts (wood, upholstery, metal, rug, mattress, floor, wall…). The 3D view resolves each part's color from the furniture file's `materials` (body: `case.color`/`case.wood`/`wood.species`/`wood_stain`/`upholstery` fabric+color/`color`; plus `base`, `top`, `hardware`; for beds, the top-level `bedding.sheets` / `bedding.pillows` colour the mattress and pillows, falling back to `defaults.mattress` / `defaults.pillow` — `bedding` sits outside `materials` so `fetch-photos.js` doesn't treat it as the product's finish) — first name found in the map wins; names not in the map are listed in the 3D HUD. Add new materials here rather than putting hex values in furniture files.
- **`<output-dir>/furniture_placements.json`** — generated output; do not hand-maintain, and don't write to it when testing (point `OUTPUT_DIR` at a scratch folder instead). Keyed by piece id: the first piece of a product is its base id = path under `furniture/` or `rugs/` minus `.json` (e.g. `room_and_board/hudson_dresser`, `9x12/nomad_9x12_olive_rug`), extra pieces are `<base>#2`, `<base>#3`… (kept contiguous; removing a piece renumbers the rest). On load a product's count = how many pieces it has in `placements`. Positions are feet-inches strings locating each piece's **back-left floor corner** in room coordinates; `rotation` is degrees clockwise from above, 0 = front faces north. `counts` and `not_placed` (products with 0 pieces) are informational. Moving a file to another folder is safe: on load an unknown saved id is adopted by the single product with the same file name. Placements for files that aren't loaded (renamed, or the server can't see them) are kept in `state.orphans` and written back unchanged rather than dropped.

- **`<output-dir>/renders/render-<timestamp>/`** — generated output, one folder per render: `pov.png` (the geometry pass the image model had to follow), `mask.png` (the flat-colour pass the frame measurements come from), `prompt.txt` / `prompt-claude.txt`, `render.jpg` or `render.png` depending on what the model returns (`render-2.…` if it returns several), and `meta.json` — the camera pose and its description, every piece with `visible` / `coverage` / `distanceIn` / `bearingDeg` / `facing` / `screenBox`, the reference photos used with their source URLs and `page_config`, the provider and model ids, Claude's findings if it audited the result, timings, usage, and `error` when the image call failed. `GET /api/renders` is this folder read newest-first. Nothing here is input: delete a folder and it's gone from the panel.

## Coordinate gotcha

Internally the client stores each piece by its **center** in **SVG screen coordinates (y down)**; room y = `room.length - screenY`. Front of a piece is local −y. Conversion to/from the file format goes through `roomOrigin` / `setFromRoomOrigin` — use those rather than converting by hand.

The 3D view uses the same screen coordinates in inches: three.js `x` = screen x (east), `z` = screen y (south), `y` up; each piece is a group at its center with `rotation.y = -rot` in radians, local front = −z.
